# Security notes

Threat model and what is not covered. Grows with each phase; see docs/spec.md
"Security, policy and control" for the designed-for threats.

## Phase 1

Covered:

- Node identity by mTLS. Private keys are generated on the node and never leave it.
- Join tokens are single-use and short-lived; the hub stores only a hash of the secret.
- The join token carries the hub CA fingerprint; the node verifies the CA before trusting anything.
- Revocation: a removed node is dropped from the bus within seconds and its certificate is refused on reconnect and on renewal.
- Agent tokens are short-lived, HMAC-signed, and bound to the node (and sandbox) they were issued to; a token copied elsewhere does not verify against another connection.
- API keys are stored hashed. Role checks go through the Policy interface and default to deny.
- Per-node NATS permissions: a node can only publish telemetry and RPC requests under its own name and only subscribe to its own control subject and inbox; publish and subscribe never overlap on a subject (reply-permission escalation, see D012). The hub validates the reply subject of every node RPC.

Not covered yet:

- Hardware-backed node keys (Secure Enclave, TPM): planned behind the identity API.
- On Windows, file modes are not applied; `local.token`, keys and the hub database rely on the ACL of the per-user config and data directories.
- Passkeys for humans: phase 6.
- Rate limiting of the enrol endpoint is a simple per-IP token bucket; there is no global limit yet.
- Revoking an agent takes effect at its next token refresh: an already issued agent token stays cryptographically valid until it expires (at most one hour). Removing a node drops its bus connection immediately, which is what carries agent traffic.
- Audit, revoked-serial and issued-certificate tables are not pruned beyond expired serials at startup.
- An individual API key cannot be revoked yet; removing the user revokes all of their keys (a `RevokeApiKey` RPC comes with the phase 2 contracts).
- Hub TLS certificates from Let's Encrypt: phase 7. Until then the hub serves a CA-signed server certificate and clients pin the CA.

## Phase 2

Covered:

- Sender identity, sequence, timestamp, hop and provenance on every message are stamped by the hub; agent-originated content is marked untrusted and adapters hand it to harnesses as quoted data with header fields sanitised so a message cannot close its own quote.
- Agent tokens are verified on every RPC and bound to the node connection in the subject; a token from another node is refused.
- Membership and policy checks on every read and write; direct channels are visible only to their participants and to admins (audited).
- Loop and cost controls: hop count along the reply chain with a per-thread limit, rate limits per sender and channel and per agent overall, caps on channels, blackboard size, long polls and RPC concurrency per node, Watch streams per user.

Not covered yet:

- A loop can restart by posting in the same thread without `reply_to` (hop returns to zero); only the rate limits bound it. Budgets (phase 3) add a cost ceiling.
- Human messages from other team members carry `untrusted: false`; the adapter shows the sender so a harness can tell owners apart, but there is no consent step before another member adds your agent to a channel or messages it.
- Audit rows for refused requests are sampled per actor; the audit table and streams are not pruned.

## Phase 3

Covered:

- Workers run as the member's own user on their own machine only; the hub refuses a parent on another node; nobody's login is used for another member's harness.
- A worker's only network credential is the agent token held inside the daemon; the worker process gets a local session id and the local token.
- Spawn requests carry no environment; the daemon's environment is inherited and `MYCEL_HOME`/`MYCEL_LOCAL_ADDR` are set last. Manifest `{{env:NAME}}` placeholders are limited to `MYCEL_FAKE_*`.
- Budgets pause rather than kill, usage never decreases, an operator pause survives exits, and a worker's home channel and parent cannot change after the first registration.

Not covered yet:

- A node that under-reports or never reports usage is not detected; usage is self-reported by the node that runs the harness.
- Claude Code workers are limited to the mycel tools; Codex workers run with workspace-write and no approvals inside a git repository, so they can edit files and run commands there.
- On Windows, workers are placed in a Job Object so stop and shutdown kill the whole tree, but this path has not run on a Windows machine yet.
- Child processes that detach from the worker's process group escape pause, stop and kill.
- Stop ends the current run only; a stopped worker may be registered again by its node. Revoke is the lasting removal.
- Any process of the node's OS user holds the local token and can read every broker credential of local agents; the local token is the same-user boundary, not a per-agent one.

## Phase 4

Covered:

- Every sandbox starts empty; the workspace is seeded by copy; mounts are validated against a deny list and symlink-resolved; the host Docker socket is never mounted.
- Egress only through the node's proxy with a per-sandbox credential; names are resolved once and dialled exactly; name-resolved loopback, private, carrier-NAT, unique-local, translated and node-own addresses are refused unless an IP is listed literally; every attempt is audited with bytes.
- Jobs are bound to the node identity they were assigned to; a removed or revoked node's jobs fail at once, and a re-enrolled name inherits nothing.
- A job's result message in a channel obeys the same posting rules as the submitter and is marked untrusted.
- Artifacts are owner-scoped with channel visibility, served as attachments with nosniff, quota- and concurrency-limited; nodes can only report on, upload for and fetch inputs of their own assigned jobs.

Not covered yet:

- Any member's job can run on any node with the `sandbox` capability, and that node's owner can read the job's environment, inputs and workspace: job environments are not secrets until phase 5 adds sharing settings and the vault.
- Nested Docker is unavailable inside gVisor-based sandboxes (Linux, Windows); phase 5's brokered host Docker covers those nodes.
- The Linux and Windows backends have only been compile-checked; their firewall and cgroup behaviour must be verified on real machines. The gVisor path needs root or CAP_NET_ADMIN plus CAP_SYS_ADMIN on the node; a fixed-verb root helper is the planned narrowing.
- Guest helper binaries inside gVisor sandboxes come from the image, so a workload can trojan them; CopyOut and Glob output is treated as untrusted.
- Child processes that detach from a fake-backend job's process group escape it (the fake backend has no isolation by design).
- On macOS the sandbox firewall is a single in-guest layer: a guest kernel local-root exploit could flush it and then reach the host's loopback services through the Lima gateway. Mitigations in place: unprivileged user namespaces disabled, no sudo, no DNS, pinned images; the images need periodic refreshing because they receive no upgrades at first boot.

## Phase 5

- Grants are hub records with a kind-specific spec, a subject (agent or job), one node and an expiry. Requests come from the subject's own agent or from a human; a channel named in a request is only honoured when it is the subject's home channel, a job's channel, or a membership added by the channel owner, an admin or the spawner, never a self-join. Auto rules without an explicit kind never match egress or docker-host; read-write mounts need `read_only: false` spelled out. Everything else is PENDING until an admin or the owner of the target node approves; approval re-checks freezes, the subject's state and the node's current offers inside the lock, can only shorten the duration and never changes the spec.
- `#approvals` is hub-only: agents can neither join nor read it, and the card carries id, kind, subject, node, duration and requester, never a reason text or a path. Both approval message types can only be posted by the hub; decisions and expiries reach the requester by direct message. Approvals are audited but not cryptographically signed (the spec says "signed"; open item for after v1).
- Attachment goes hub → node by `AttachGrant`; the node validates again (node name, subject, expiry, mounts via ResolveMount and once more at sandbox creation, egress rules), refuses anything its local ceiling does not offer and reports `grant.revoked`. A node refusal revokes the grant on the hub. Returning nodes are re-sent every attach and detach; nodes expire grants on their own clock, also across sleep, and remember local revocations until the hub acknowledges them.
- Brokers are per-grant credentials, not sockets. Ollama: one opaque token per grant, model allowlist, requests per minute, `max_tokens` enforced by clamping `num_predict` and cutting streams, in-flight and connection caps, slow-body timeouts, aborted streams still accounted once. GPU: leases per device, exclusive or time-sliced, detach kills processes still on the device except the daemon's own tree and never while a neighbour still holds a time-slice. Docker: every create and exec body is decoded into typed structures and rebuilt from allowed fields only (so case-variant or duplicate keys cannot smuggle `Privileged`), `NetworkMode` is always `none`, no port bindings, no host paths beyond the grant's mounts, capped CPU/memory/pids/containers under a per-grant cgroup parent, `DeviceRequests` only with a gpu grant and only the leased ids, labels for sweep, a pull rate limit, and the socket directory must be a real directory owned by the daemon user. The host `docker.sock` is never mounted anywhere.
- Sandboxes reach brokers only through the egress proxy: per-sandbox aliases (`ollama.mycel.internal:80`, `docker.mycel.internal:2375`) map to the broker's loopback listener, so the allowlist stays default-deny and no guest routing is needed.
- The node owner's ceiling: `PUT /api/local/sharing` may only tighten relative to the settings the hub last sent, is persisted locally, enforced by admission and every broker while the hub is unreachable, and reported back with `node.sharing`. Removing an offer detaches open grants of that kind at once. A detector that cannot tell whether the owner is idle reports an explicit unknown state: `when: idle` then stays inactive and `local_first` pauses nothing, so headless nodes are not stuck.
- Kill switch: an operator pause (phase 3), a channel freeze by its owner or an admin (agents homed there pause, posts are refused), and the network freeze, which is admin-only in both directions: the hub stops dispatching queued jobs, refuses posts, jobs, grant requests and approvals, pauses every agent and sends `Freeze` ahead of anything else in every node's control queue; nodes stop sandboxes and workers (SIGSTOP; a no-op on Windows), brokers answer 503, and the state is persisted so a restart with the hub down stays frozen. An operator pause survives an unfreeze. The hub re-sends the current freeze state on every full-inventory heartbeat, so a node that missed an unfreeze recovers.
- The approvals page uses HttpOnly, Secure, SameSite=Strict cookies, a per-session CSRF token, an Origin and `Sec-Fetch-Site` check, a login rate limit and at most 8 sessions per user; the API key travels only in the login POST body.
- Boundaries worth knowing: every process of the node's OS user holds the local token and can read any local broker credential (the local token is the same-user boundary); a job's wall clock keeps counting while it is paused by `local_first` or a freeze; the Docker and GPU brokers are tested against fakes only (no engine or GPU on the development machine); MIG slice handling is a best guess until run on real hardware.

## Phase 6

- The UI is a static single-page app embedded in the binary and served by the hub (admin UI) and by every node daemon on its loopback address (node UI). Its content security policy allows only same-origin scripts, styles, fonts and connections; there are no inline scripts or styles, no external origins, no analytics, and the service worker precaches static files only (never API responses or tokens).
- Hub sessions: an HttpOnly, Secure, SameSite=Strict cookie (Path `/`, 24 h, at most 8 per user) created by the API-key form or a passkey login. Every cookie-authenticated request that is not a plain GET, including every Connect RPC, must carry the session's CSRF token in `Mycel-Csrf` and pass a same-origin check (a `null` or mismatched Origin counts as cross-site); otherwise it runs unauthenticated. API keys in `Authorization` are unaffected. Streams re-check the session, the user's role and (for node scopes) certificate revocation on every heartbeat; `logout-all` ends every session of a user.
- Passkeys (WebAuthn, discoverable credentials): challenges are single-use and expire after two minutes; login ceremonies are keyed by a random id in a short-lived cookie, not by IP; the user handle must match the credential's owner; signature counters that do not increase are refused; the last passkey cannot be removed while the user has no API key; login begin never reveals which users exist; passkeys are off when the hub's RP id is an IP address.
- Push notifications carry ids and kinds only. Subscription endpoints must be HTTPS on a public DNS name; the sender refuses loopback, private, CGNAT, NAT64, documentation and test ranges, follows no redirects, and never logs endpoint URLs. One user cannot claim another user's endpoint. The VAPID private key lives in the hub directory with mode 0600.
- Node read scope: a request over a node's mTLS certificate carrying `Mycel-Scope: network:read` acts as the node owner's user with the role forced to member and may only call a fixed read-only method list (checked on the hub and again in the daemon's proxy); everything else is refused and audited. Without the header a node certificate has no user rights. The daemon's `/api/hub/*` proxy requires the local token, forwards only an allowlisted header set (never cookies or Authorization), strips Set-Cookie from responses, limits bodies to 1 MiB and times out idle streams.
- Local sign-in: `mycel ui` never puts the local token on a command line or in a URL; it trades a single-use 60 s code for the token inside the app, which keeps it in sessionStorage only. The local token now also opens the owner's network-wide read view, so every process of the same OS user can read what the owner can read (D024's same-user boundary).
- Events, search and audit replay apply the same visibility as the matching List RPC; direct-message events and search hits reach channel members only (admins read DMs through the audited ListMessages path); audit rows carry their owner so members see only their own actors; message bodies are rendered as text only in the UI (untrusted ones as quoted blocks, links never clickable to external origins).
- Boundaries worth knowing: the event ring and pending queue are bounded by bytes (64 MiB each) and search is windowed and rate-limited, but a hub with a very large history still pays for LIKE scans; the browser smoke test runs only where Chrome exists; a node's egress records reach the hub only as totals until the acceptance package forwards them.

## Phase 7

- mDNS (known hazard of userland responders): a userland mDNS responder that announces A/AAAA records for the machine's own host name collides with the system responder; on macOS mDNSResponder then renames the computer (`<name>-2.local`). Mycelium therefore advertises through the system responder (`dns-sd -R` on macOS, `avahi-publish-service` on Linux when installed) and uses its userland responder (Windows, Linux without avahi or when avahi exits within a second) only with a dedicated host name `mycel-hub-<8 hex>.local`, never the machine's name; a unit test checks the names it answers for. The responder child runs under `/bin/sh -c <fixed script> -- <command> <args>`: the arguments are positional parameters, never parsed by the shell (a test passes `$(...)`, backticks and `;`). The supervisor kills the child when its stdin, a pipe from the hub, closes, so a hub that dies (even by SIGKILL) takes the registration with it; the child's pid is kept in `<hub dir>/mdns.pid`, and a hub that starts kills a stale responder named there only if that process still runs `dns-sd` or `avahi-publish-service` for `_mycel-hub._tcp`. Nothing secret is in the TXT record (trust domain, URLs, CA fingerprint), and discovery answers are trusted only through the CA fingerprint and the pinned-CA TLS handshake. Tests stay off the network: hub tests replace the advertiser, the e2e hubs run with `--no-mdns` (and `MYCEL_NO_MDNS=1` disables advertising for a whole process), the responder tests run a fake `dns-sd` script, and browsing and real multicast run only with `MYCEL_TEST_MDNS=1` (advertising on Linux CI only).
- Pinned CA only: every connection that trusts a hub verifies its certificate against the hub CA the client pinned (the join token's fingerprint, node.yaml's `ca.crt`, config.yaml's `ca_cert_pem`, the hub directory's `ca.crt`), never the system roots: discovery probes (node and join), Enrol, the bus, a redirect target the node switches to, and the CLI's check of a redirect target (`/healthz` and the bus handshake). A public certificate for a hub's name (from a relay or any CA) is therefore worthless to an attacker. Tests inject a "system" root into the test process (`x509.SetFallbackRoots` with `GODEBUG=x509usefallbackroots=1`, checked to be trusted by a default client) and require each of those paths to refuse a server whose certificate chains to it. The relay package follows the same rule.
- Redirects: signed by the hub CA key over a fixed payload (trust domain, hub URL, bus URL, issued_at). Signer and verifier both reject control characters in any field and a bus address that is not `host:port` / `tls://host:port` with a numeric port 1-65535. Nodes, CLIs and joins accept a redirect only after verifying it against the CA they pinned, within 24 h in the past and 5 min in the future; nodes (node.yaml) and the CLI (config.yaml `redirect_issued_at`) never accept one older than the last they followed. A node keeps its current connection and address until the new bus accepts it over TLS verified against the same CA, and only then stores the new address; a target that refuses the node's certificate is retried with backoff and never treated as revocation. So a stolen or mistaken redirect can at worst make nodes retry an address that fails the handshake. `mycel hub redirect` checks the target (pinned-CA `/healthz` and bus handshake) before signing, unless `--force`. A moved hub whose stored redirect is dated more than 5 min ahead (the clock jumped back) signs it again with the current time and logs the jump. Moved mode cannot be left through the API. The CA key signs redirects inside the hub; it is never logged or audited.
- Export files hold the CA key: streamed AES-256-GCM in 1 MiB segments under an argon2id key (t=3, 64 MiB, p=4) from a passphrase of at least 12 characters that is read from a file or the terminal, never a flag, and never logged. Every segment authenticates the header (magic, salt, base nonce) and a last-segment flag; nonces are the base XOR the segment counter, so tampering, reordering, truncation (also at a segment boundary) and trailing data all fail. The live export route needs an admin API key on a connection from the hub machine itself (remote and local address both loopback, or, for a hub listening on one non-loopback address, remote IP equal to local IP; a loopback peer on a non-loopback local address, i.e. a tunnel, is refused, and the CLI then says to stop the hub to export), serves one export at a time, returns only the database snapshot and stream snapshots, and is audited (`hub.export`; offline exports are audited after the seal with their outcome; imports `hub.import`, redirects `hub.redirect`). A running hub holds `<hub dir>/hub.lock` (flock); offline export and offline redirect must take it, so they never run beside a hub, and the CLI treats only a refused connection as "stopped". Import requires a missing or empty hub directory that is not a symbolic link (nor is its parent), restores into a fresh temporary directory next to it (refusing archive entries outside its fixed list, non-regular entries, path tricks and symlinked directories on the way) and renames it into place only on success, so a failed or damaged import leaves nothing behind. Import never restores `relay.url` (a relay token belongs to one hub). Stale `.export-*` scratch directories are removed when the hub starts.
- Known limits: a node that cannot reach its hub follows any address advertising the pinned CA fingerprint that also passes the pinned-CA handshake, which an attacker on the LAN cannot fake but can point at a copy of the hub restored from an export.
- Relay tunnel (`mycel relay`, internal/tunnel/doc.go): the relay forwards TCP and never terminates the hub's TLS, so it sees ciphertext only. The hub pins the relay certificate by the fingerprint in the relay URL and authenticates with a token the relay stores only as a SHA-256. The relay URL carries that secret: it is printed once, read by the hub from stdin (`mycel hub tunnel set -`, `mycel hub init --tunnel -`), kept in `relay.url` (0600) and never written to hub.yaml, logs or audit. One hub per relay: a second token needs `--replace`, and while a hub is attached a hello for another hub name is refused.
- Nodes and CLIs never trust the system roots for the hub (D026): they verify the hub's server certificate against the pinned hub CA only, host name included. A relay operator controls the public port 443 and could obtain a publicly trusted certificate for the hub's name (TLS-ALPN-01), so trusting public roots would let it capture join tokens at `mycel join`, admin API keys from the CLI and run a fake bus. The hub's ACME certificate is for browsers only: the API and bus present it unless the ClientHello lists the ALPN marker `mycel-ca`, which every node and CLI connection sends; the marker is never negotiated.
- The relay is trusted for the source address it reports for each forwarded connection: per-IP rate limits behind the relay use it, and audit records such addresses with `remote_via_relay: true`. Bus connections through the tunnel reach the bus from the hub's loopback forwarder, so the bus sees a loopback source for them (bus authentication is the node certificate, not the address).
- Relay limits: 1024 forwarded connections per hub (a fixed budget of yamux stream windows), 64 concurrent and 64 new per second per source (IPv4 address or IPv6 /64), 10 minutes idle; the control listener holds at most 64 unanswered connections with a 10 s handshake timeout and 4 new per second per source; the per-source tables evict the least recently seen source instead of refusing new ones. The hub holds at most 64 tunnel streams waiting for their header. Strings from the relay are stripped of control characters and truncated before they are logged, stored or printed.
- ACME is never requested inside a client hello: a background issuer starts once the hub is reachable (through the relay: after the first attach), backs off from 1 minute to 1 hour and waits at least 10 minutes after any failure, so probes cannot use up the CA's validation limits. Until then browsers get the CA-issued certificate.
